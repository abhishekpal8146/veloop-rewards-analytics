# VELOOP Rewards — User Analytics Specification

## 1. Document Overview

**Deliverable:** D04 — User Analytics Specification  
**Work Package:** B — User Analytics

### 1.1 Purpose

This document defines the user identity requirements and analytical data structure needed to track the user lifecycle within the VELOOP Rewards platform.

It covers registration, login, onboarding, account lifecycle, and user activity tracking.

### 1.2 Scope

The specification focuses on:

- Identifying users consistently across multiple activities.
- Tracking login events and user sessions.
- Recording important onboarding milestones.
- Monitoring account lifecycle changes.
- Supporting reliable user analytics and reporting.

**Important:** This document defines proposed analytics requirements. Actual implementation and source availability must be verified before treating these requirements as confirmed system capabilities.

## 2. B1 — User Identity Requirements

### 2.1 Stable User ID

- **Purpose:** Uniquely identifies an individual user across the platform.
- **Example:** `USR_1001`
- **Requirement:** Required.
- **Validation:** Must be unique, non-empty, and persistent.
- **Reason:** Enables user activity to be linked across registration, login, onboarding, and subsequent interactions.

### 2.2 Event ID

- **Purpose:** Uniquely identifies an individual user activity or event.
- **Example:** `EVT_001`
- **Requirement:** Required for tracked events.
- **Validation:** Must be unique for each event record.
- **Reason:** Prevents separate activities from being confused or merged.

### 2.3 Session ID

- **Purpose:** Groups activities performed during a single user session.
- **Example:** `SES_001`
- **Requirement:** Required where session tracking applies.
- **Validation:** Must uniquely identify a session and associate relevant events with it.
- **Reason:** Helps analyse session activity, duration, and engagement.

### 2.4 Transaction ID

- **Purpose:** Uniquely identifies an individual transaction, such as a reward redemption.
- **Example:** `TXN_001`
- **Requirement:** Required for transaction records.
- **Validation:** Must be unique for each transaction.
- **Reason:** Supports accurate transaction tracking and prevents duplicate or mixed transaction records.

### 2.5 Identity Management Rules

1. Each user must have one stable User ID.
2. The User ID must remain unchanged when the user's email address or other contact information changes.
3. Email addresses should not be used as the primary analytics identifier.
4. Each tracked event must have its own Event ID.
5. Each session should have a distinct Session ID.
6. Each transaction must have its own Transaction ID.
7. Different users must never share the same Stable User ID.

### 3.2 How to read the field tables

- **Field** — the column name exactly as it appears in the workbook.
- **Type** — taken from the workbook's own data dictionary where one exists; otherwise marked *(observed)* and inferred from sample rows actually read.
- **Required?** — from the workbook data dictionary: Required / Optional / Conditional / Derived. "Not specified" means the workbook's data dictionary does not cover this field.
- **Purpose** — the data dictionary definition where available; otherwise a short description of the role the field plays in its sheet.
- **Source** — the workbook and sheet(s) where the field was observed.
- **Validation** — the rule stated in the workbook data dictionary; "Not defined in data dictionary" where the workbook provides none.
- **Status** — *Evidenced (simulated)* means the field is present in the named simulated workbook(s); *Unverified (production requirement)* means B1 requires it but it is absent from both workbooks.

#### Session ID vs Event ID — not interchangeable

- A **session** is one block of activity by one user: `02_Sessions` holds one row per session (7,913 rows).
- An **event** is one specific action inside a session: `03_Feature_Events` holds one row per event (35,704 rows).
- The event sheet carries **both** identifiers: `event_id` is unique per row, while `session_id` repeats across the rows that belong to the same session (for example, `SESS0000001` contains events `EVT00000001`, `EVT00000002`, `EVT00000003`, …).
- In short: `session_id` answers *"in which session did this happen?"* and `event_id` answers *"which specific action was this?"*. They must never be used interchangeably — grouping on `session_id` merges all actions of a session, and `event_id` alone cannot recover session grouping (only the `session_id` column on the event row can).

**Closest thing to a transaction in the simulated data:** `reward_status` in `05_Task_Activity` (observed values `Credited`, `Not Credited`) records a reward-credit outcome for a task activity. It is **not** a transaction identifier and must not be treated as `transaction_id`.

### 3.10 What is evidenced, and what is not

- **Evidenced in the simulated datasets:** every field in §3.4–§3.9, plus the identifiers `user_id`, `session_id`, and `event_id` (§3.3).
- **Not evidenced in either workbook:** `transaction_id` (B1 §2.4). No transaction or redemption identifier, and no transactions table, exists in the simulated data; `reward_status` (§3.8) is the only reward-credit signal, at task level.
- **Login tracking:** there are no per-login event records in either workbook. The only login signal is `last_login_datetime` (Task 01), so B1's "tracking login events" remains unverified against the provided data.
- **Simulated vs production:** every field marked *Evidenced (simulated)* is proven only for the synthetic workbooks. Per each workbook's README, the data is fictional and must not be presented as actual VELOOP users, sessions, events, or production analytics. Production availability of all B2 fields remains to be verified.

## 4. Data Quality and Validation Principles

- Identifiers must not be empty when required.
- Unique identifiers must not be duplicated.
- Events must be associated with the correct user.
- Session and transaction relationships must be maintained.
- Missing or unavailable source information must be marked for verification rather than assumed.
- The Task 01 workbook ships a `Users_Messy_Audit` sheet that, per its README, intentionally contains controlled missing values, malformed dates, and duplicates. The validation rules in §3 therefore describe the clean sheets; the audit sheet should be used to test validation logic, not as trusted data.

## 5. Verification Status

The identifiers and validation rules in this document represent proposed analytics requirements. Their availability in the actual VELOOP platform must be verified against the relevant data sources and implementation.

As of 2026-11-13, the B2 field set in §3 was cross-checked, in read-only mode, against the two workbooks in `source datasets/`. Fields marked *Evidenced (simulated)* were confirmed to be present in those workbooks, which are explicitly simulated data; their availability on the production VELOOP platform remains unverified.

3. **`feature_name` casing:** `03_Feature_Events` uses Title case (e.g. "Missions", "Leaderboard", "Wallet"). `10_Event_Data_Quality_Audit` contains mixed casing: alongside the same Title-case names it has five lowercase variants — `daily reward`, `leaderboard`, `missions`, `wallet`, `watch ads`.
4. **Fields marked "Not specified"** (e.g. `platform`, `country`, `device`, and most non-dictionary Task 02 columns) have no type/requirement/validation definitions in the workbook data dictionaries; the types shown are inferred from observed values only.
5. **Controlled value lists** for categorical fields (e.g. the full sets of `milestone_type`, `event_status`, `task_category` values) were not enumerated; only values observed in the sample rows are cited.
6. **Onboarding milestones:** only three sample rows of `06_Milestones` were read; whether onboarding-specific milestone types exist there is unverified.
